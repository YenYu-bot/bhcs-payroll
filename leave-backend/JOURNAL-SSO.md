# 教室日誌登入橋接（未部署的候選版本）

員工入口使用既有教室日誌的短帳號及密碼，密碼只送往教室日誌原用 Firebase Authentication，不傳給請假服務，也不另存。Firebase 函式只收到教室日誌當次登入權杖，檢查簽章、來源專案、帳號狀態、密碼重設時間、現行教師文件及登入對照。不讀學生名冊、日誌內容、薪資或照片，並使用該員工自己的來源權杖讀取指定文件，不要求教室日誌專案授予管理角色。

請假 Auth UID 固定以 leave_ 開頭並使用隨機 ID，不使用姓名、短帳號、來源 UID 當正式請假歸屬。不得把教室日誌主管直接設成請假主管。主管照原案走 Google 登入及請假成員表。員工必須在兩份受控記錄都由有權管理者核對，員工本人不能改：
- `journalBindings/{journalAuthUid}`：`leaveUid`（請假專案隨機身分）、`active`、`version`（正整數）。
- `leaveMembers/{leaveUid}`：`role: staff`、`active`、`journalSourceUid`、`journalUserId`、`journalBindingVersion`、`employeeId`（既有薪資 ID）、`label`。兩份記錄版本要一致。

教室主管「重設密碼」會給同一短帳號新 UID；由授權主管確認是同一員工後，新增新 UID 的對應、停用舊對應、更新請假會員版本及來源 UID，應在同一 Firestore 交易。舊會話透過新版存取規則立即失效，並撤銷請假 Auth refresh token。離職須立即在請假端停用會員與對應並撤銷會話；僅在教室刪除的未同步例外最多保留現有 10 分鐘權限，到期不能續。照片視窗隨登入有效性清除。不得用同名或再次出現的短帳號自動繼承假單。

## 部署順序與費用
1. 僅對 bhcs-leave 部署。使用專用 Functions runtime service account（不要建立使用者管理的私鑰），在 bhcs-leave 授最低限度 Firestore 讀取；供 Firebase Admin 簽發權杖的權限只授予專用帳號在自身簽署者，不授教室日誌 IAM。正式部署必須先確認函式執行身分。來源 API key 是教室日誌公開 Web 設定，不是管理憑證。
2. 將 web app 公開 Firebase 設定與來源配置填入 config.mjs；主管 Google 登入的允許網域須包含實際主管入口。仍以不同網域部署員工與主管入口。
3. 先在模擬器跑權限與合成身份重綁測試。部署指定專案的新版規則（員工需短效教室身分租約），再部署函式。不加常駐執行個體，最大 1 個，函式只存取指定兩個來源文件及驗證端點。清理舊建置產物；計費預算通知並非上限，如需另設預算或專用費用上限，由負責人確認。驗證函式可用、安全未開啟員工前只測非授權情形。部署員工 Hosting 和主管介面前，準備至少兩個已獲准試行帳號及其核實 UID 對應。
4. 用合成照片測：兩位老師互看資料被拒、同一員工重綁後可查歷史、同名新任職者看不到舊資料、兩裝置停權、要求補件後審核，以及薪資面重試不重複入帳。保留現行教室日誌入口，不把任何密碼或真實證明寫入測試或 Git。
